# Release v1.0.8 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship codeo v1.0.8 from `main` as it stands (release PR, clean-clone test, tag, GitHub Release), then pin this project to v1.0.8 so its container and sessions run it.

**Architecture:** Two pull requests, as for v1.0.7. The release PR comes from its own branch `release/v1.0.8`, cut from `origin/main` in a git worktree: four files and no dossier, so the required `qc-verdict` check passes (it fails a head that carries a live dossier). This workflow branch carries the pin, the plan and the dossier, and `/codeo:close` opens its PR after the tag exists. Steps that are the engineer's (merges, tag push, container rebuild) are tasks that stop and wait.

**Tech Stack:** `git`, `gh`, `jq`, `sed`, `awk`, `bash tests/run.sh`, `claude plugin list`.

**Spec:** `.codeo/146/init.md` (`## Outcome`: the eight acceptance criteria); `docs/release-checklist.md` steps 6-8; `.codeo/146/plan.md` Q1-Q3.

```mermaid
flowchart LR
  T1[1 release PR<br/>release/v1.0.8] --> T2[2 you merge]
  T2 --> T3[3 clean-clone test]
  T3 --> T4[4 you tag + push]

  T5 --> T6[6 pin on this branch<br/>plugin.ref]
  T6 --> T7[7 you rebuild, agent<br/>checks version]
```

## Global Constraints

- Release scope is `main` as it stands when the release PR is opened (`6ccd510` at planning). #143, #144, #145, #138, #149 and #151 are all closed and merged. Any other issue ships later.
- The release PR changes exactly four files: `.claude-plugin/plugin.json`, `CHANGELOG.md`, `README.md` and `tests/install.test.sh`. `.claude-plugin/marketplace.json` carries no version.
- `CHANGELOG.md` gets three edits and no other (plan Q1, Q3):
  1. Line 3 `## Unreleased` becomes `## v1.0.8 — <date>`, the day the PR is opened (corrected before merge if it merges on a later day).
  2. Line 5 `Config schema: 1` becomes ``Config schema: 1 (adds the optional `issue.priority` key; a config without it is unchanged)``.
  3. The bullet that starts `- Leftovers from the live signal work, documentation and tests only.` (#118, merged after the `v1.0.7` tag, now the last bullet but one of `## v1.0.7`) moves, unchanged, to the end of the `## v1.0.8` section: after the `codeo rm` bullet, with one blank line before it as the section's other bullets have.
  The `Shared state:` and `Safe to bump mid-workflow: yes` lines stay as written: they were checked at planning against the diff since `v1.0.7` of `scripts/lock.sh`, `scripts/live.sh`, `scripts/inflight.sh`, `scripts/dossier-check.sh` and `docs/dossier.md`. All other bullets are released as they stand.
- `README.md`'s examples move one version up (plan Q2): every `1.0.7` becomes `1.0.8` and every `1.0.6` becomes `1.0.7`. `tests/install.test.sh` takes the same substitution, because its stubs are what the README's output blocks and JSON snippet are compared with. Nothing else in either file changes. The substitution was dry-run at planning on `6ccd510`: `bash tests/install.test.sh` ended `all cases passed`.
- The tag push, both PR merges and the container rebuild are the engineer's. The agent never merges or tags. The agent publishes the GitHub Release only after the engineer says the tag is pushed. A pushed tag is never moved.
- The tag is lightweight, as `docs/release-checklist.md` step 7 writes it and as `v1.0.5` to `v1.0.7` are: `git tag v1.0.8 <SHA>`.
- The pin moves only after the tag exists: `.devcontainer/scripts/plugins.sh` checks the pin on GitHub before replacing codeo.
- The GitHub Release follows checklist step 8: title `v1.0.8`, notes are the changelog section only, never `--generate-notes`.
- Tasks 2, 4 and 7 mark `Runs on: the engineer's host`; their commands are single commands a shell passes through unchanged (the lock's host is `container`).
- No shared environment, so no task carries `Needs lease:`. No invariants document, no `wiki` module, no exclusive resources, so nothing is leased. No other workflow is in flight.
- Documentation: the change moves one page, `README.md` (its installer examples, Task 1). No page under `docs/` describes a version or the pin as current; `docs/dev-environment-sbx-evaluation.md` names `1.0.6` only as recorded observations, which stay as observed. Changing the release checklist is out of scope (issue).
- #132 (tests only) gets no changelog bullet.
- `/codeo:close` opens one PR per workflow from this branch; the release PR is opened by `/codeo:implement` from `release/v1.0.8` and is a different head.

## Review Focus

- The release branch is cut from `origin/main`, not from this branch: a diff beyond the four files, or any `.codeo/` change, fails `qc-verdict` and drags a live dossier into `main`.
- The substitution order matters: `1.0.7` → `1.0.8` first, then `1.0.6` → `1.0.7`, in one `sed` call. The other order turns every version into `1.0.8`. It runs on `README.md` and `tests/install.test.sh` only, never on `CHANGELOG.md`.
- `main` may have moved between this plan and Task 1: Task 1 reads `## Unreleased` and the `## v1.0.7` section before editing, every bullet under `## Unreleased` ships, and the line numbers here (3, 5, 56) are re-read, not trusted.
- The clean-clone test must run at the merge commit, not at `main`'s tip if `main` moved after the merge.
- A lightweight tag has no `^{}` line in `git ls-remote --tags origin`: criterion 5 is read from the plain `refs/tags/v1.0.8` line.
- The Release notes file must not start with the heading and must not be generated: its first line is the edited `Config schema: 1 (adds …)` line, and it holds the moved #118 bullet.
- A stale `CODEO_ROOT` or an old session: the version check runs in a session started after the rebuild, and `claude plugin list` may show a user-scope and a project-scope `codeo@codeo`; Task 7 records either one that is not 1.0.8.
